# Lab 18: Helm internals and advanced operations

**Start:** Lab 17 complete (`lab-17-complete`). An active Kubernetes cluster with Helm v3.17+ installed and the `helm-diff` plugin.
**Goal:** Master Helm's internal architecture and advanced operational recovery: inspect and decode release Secrets by hand, understand three-way strategic merge patch and live drift behavior, adopt unmanaged Kubernetes resources into a Helm release using `--take-ownership` and manual metadata, recover releases blocked by deprecated/removed Kubernetes APIs with `mapkubeapis`, and prepare charts for Helm 4's Server-Side Apply (SSA).

---

## Why Helm internals matter

To a novice, Helm feels like a black box: you run `helm upgrade`, manifests apply, and occasionally an obscure error appears (`another operation is in progress`, `invalid ownership metadata`, or `resource mapping not found`).

In reality, Helm has **no server-side daemon**, **no database**, and **no operator**. Helm is a client-side CLI that translates templates into Kubernetes API requests and stores its entire release history directly inside standard Kubernetes `Secret` objects.

When you understand the exact storage format, the three-way merge patch algorithm, and how Helm interacts with the Kubernetes API server, mysterious failures turn into simple, solvable operational tasks.

## Part A: Release state storage & dissecting release secrets by hand

Helm stores release revisions as Kubernetes `Secret` objects in the namespace where the release is installed.

### Step 1: Create a dedicated practice namespace and install a baseline release

Create a clean namespace `helm-internals` and install `charts/nginx-demo`:

```bash
kubectl create namespace helm-internals
helm install internals-demo charts/nginx-demo -n helm-internals --set replicaCount=1
```

Verify the release is deployed:

```bash
helm list -n helm-internals
```

### Step 2: Inspect release storage Secrets

List all Secrets owned by Helm in `helm-internals`:

```bash
kubectl get secrets -n helm-internals -l owner=helm
```

Expected output:

```text
NAME                                   TYPE                 DATA   AGE
sh.helm.release.v1.internals-demo.v1   helm.sh/release.v1   1      30s
```

Notice the naming convention:

```text
sh.helm.release.v1.<RELEASE_NAME>.v<REVISION>
```

Inspect the Secret's metadata and labels:

```bash
kubectl get secret sh.helm.release.v1.internals-demo.v1 -n helm-internals -o yaml
```

Observe key metadata fields:

- `type: helm.sh/release.v1`
- `metadata.labels.name: internals-demo`
- `metadata.labels.owner: helm`
- `metadata.labels.status: deployed`
- `metadata.labels.version: "1"`
- `data.release`: A large base64-encoded string containing the entire release payload.

### Step 3: Decode the release payload without Helm

Why is Helm's payload doubly base64-encoded?

1. **Helm storage driver layer:** Helm serializes the release object to JSON, compresses it with `gzip`, and base64-encodes the binary bytes into a string.
2. **Kubernetes Secret layer:** Kubernetes base64-encodes all values inside `Secret.data`.

To extract the raw JSON release object using standard Linux CLI tools:

```bash
kubectl get secret sh.helm.release.v1.internals-demo.v1 -n helm-internals \
  -o jsonpath='{.data.release}' | base64 -d | base64 -d | gzip -d | jq .
```

Inspect the top-level keys in the decoded JSON:

```bash
kubectl get secret sh.helm.release.v1.internals-demo.v1 -n helm-internals \
  -o jsonpath='{.data.release}' | base64 -d | base64 -d | gzip -d | jq 'keys'
```

Output:

```json
[
  "chart",
  "config",
  "hooks",
  "info",
  "manifest",
  "name",
  "namespace",
  "version"
]
```

Inspect what is stored inside each key:

- **`.config`:** The exact user values passed via `--values` or `--set`:

  ```bash
  kubectl get secret sh.helm.release.v1.internals-demo.v1 -n helm-internals \
    -o jsonpath='{.data.release}' | base64 -d | base64 -d | gzip -d | jq '.config'
  ```

- **`.manifest`:** The exact rendered Kubernetes YAML applied to the cluster:

  ```bash
  kubectl get secret sh.helm.release.v1.internals-demo.v1 -n helm-internals \
    -o jsonpath='{.data.release}' | base64 -d | base64 -d | gzip -d | jq -r '.manifest' | head -n 35
  ```

- **`.info`:** Deployment timestamps, notes, and release status (`deployed`, `superseded`, `failed`, `pending-upgrade`).

## Part B: The three-way strategic merge patch & live drift

When you run `helm upgrade`, Helm does not simply run `kubectl apply` or replace objects. Helm calculates a **Three-Way Strategic Merge Patch** using three inputs:

1. **Base:** The `.manifest` stored in the previous release Secret (`sh.helm.release.v1.<release>.v<N-1>`).
2. **Live:** The actual object currently live on the Kubernetes cluster.
3. **Target:** The newly rendered manifest generated by the upgraded chart and values.

```text
       [ Base: Previous Secret Manifest ]
                  /              \
                 /                \
                v                  v
    [ Live Cluster State ]    [ Target Rendered Manifest ]
                \                  /
                 \                /
                  v              v
        [ 3-Way Strategic Merge Patch applied to Cluster ]
```

### Step 1: Out-of-band annotation (Field absent in Base & Target)

Imagine an external system (monitoring agent, service mesh, or incident responder) annotates the live Deployment:

```bash
kubectl annotate deploy -n helm-internals internals-demo-deployment ops.company.com/incident-id="INC-9901"
```

Verify the annotation is present on the live cluster:

```bash
kubectl get deploy -n helm-internals internals-demo-deployment \
  -o jsonpath='{.metadata.annotations.ops\.company\.com/incident-id}{"\n"}'
```

Output: `INC-9901`.

Now upgrade the release with a scale change:

```bash
helm upgrade internals-demo charts/nginx-demo -n helm-internals --set replicaCount=2
```

Inspect the Deployment after the upgrade:

```bash
kubectl get deploy -n helm-internals internals-demo-deployment \
  -o jsonpath='{"replicas: "}{.spec.replicas}{", incident-id: "}{.metadata.annotations.ops\.company\.com/incident-id}{"\n"}'
```

Output:

```text
replicas: 2, incident-id: INC-9901
```

**Why was the annotation preserved?**
Because the chart's template did not specify `ops.company.com/incident-id`. In a three-way merge:

- `Base`: no annotation
- `Live`: has annotation
- `Target`: no annotation
- **Result:** Since `Target` did not actively delete or modify the annotation from `Base`, `Live` wins. Out-of-band cluster modifications to unmanaged fields are safely preserved!

### Step 2: Out-of-band drift on a managed field (`spec.replicas`)

Now manually scale the deployment directly using `kubectl`:

```bash
kubectl scale deploy -n helm-internals internals-demo-deployment --replicas=5
```

Verify live replicas:

```bash
kubectl get deploy -n helm-internals internals-demo-deployment -o jsonpath='{.spec.replicas}{"\n"}'
```

Output: `5`.

Now re-run `helm upgrade` using the chart's values (`replicaCount=2`):

```bash
helm upgrade internals-demo charts/nginx-demo -n helm-internals --set replicaCount=2
```

Check the live replicas again:

```bash
kubectl get deploy -n helm-internals internals-demo-deployment -o jsonpath='{.spec.replicas}{"\n"}'
```

Output: `2`.

**Why did Helm reset `replicas` back to 2?**
Helm manages the `spec.replicas` field. Because `Target` specifies `replicas: 2`, Helm enforces the desired state declared in the chart.

## Part C: Adopting existing Kubernetes resources into a Helm release

A common migration challenge occurs when Kubernetes resources were created manually or by legacy scripts, and you now want to bring them under Helm management.

### Step 1: Observe the collision failure

Create an unmanaged Service that matches the name `charts/nginx-demo` would generate for a release named `legacy-app`:

```bash
kubectl create service clusterip legacy-app-service --tcp=80:80 -n helm-internals
```

Now attempt to install `legacy-app` using Helm:

```bash
helm install legacy-app charts/nginx-demo -n helm-internals
```

Expected error:

```text
Error: INSTALLATION FAILED: Unable to continue with install: Service "legacy-app-service" in namespace "helm-internals" exists and cannot be imported into the current release: invalid ownership metadata; label validation error: missing key "app.kubernetes.io/managed-by": must be set to "Helm"; annotation validation error: missing key "meta.helm.sh/release-name": must be set to "legacy-app"; annotation validation error: missing key "meta.helm.sh/release-namespace": must be set to "helm-internals"
```

Helm protects you from accidentally taking over or overwriting unmanaged cluster resources. It requires three ownership markers:

1. Label: `app.kubernetes.io/managed-by: Helm`
2. Annotation: `meta.helm.sh/release-name: <release-name>`
3. Annotation: `meta.helm.sh/release-namespace: <release-namespace>`

### Step 2: Adopt using the `--take-ownership` flag

In Helm v3.17+, Helm introduced the `--take-ownership` flag:

```bash
helm install legacy-app charts/nginx-demo -n helm-internals --take-ownership
```

Verify that the installation succeeded and Helm injected ownership metadata:

```bash
kubectl get svc -n helm-internals legacy-app-service -o yaml | grep -A 3 -B 1 "meta.helm.sh"
```

Output:

```yaml
  annotations:
    meta.helm.sh/release-name: legacy-app
    meta.helm.sh/release-namespace: helm-internals
```

> [!WARNING]
> **Adoption Transfers Lifecycle Ownership:**
> Once an unmanaged resource is adopted into a Helm release, Helm assumes complete lifecycle management over it. If you later execute `helm uninstall <release>`, Kubernetes will delete the adopted resource along with the release unless it has been annotated with `"helm.sh/resource-policy": "keep"`. Furthermore, Helm reconciles the adopted resource's specification to match the chart's template (e.g. rewriting Service selectors to match the release's Pods).

### Step 3: Manual adoption via `kubectl` metadata injection

If you are running in CI or automation where `--take-ownership` is restricted, you can adopt resources by adding the labels and annotations before running Helm:

```bash
# 1. Create unmanaged ConfigMap
kubectl create configmap adopt-demo-config --from-literal=status=legacy -n helm-internals

# 2. Inject Helm ownership metadata
kubectl annotate configmap adopt-demo-config -n helm-internals \
  meta.helm.sh/release-name=adopt-demo \
  meta.helm.sh/release-namespace=helm-internals
kubectl label configmap adopt-demo-config -n helm-internals \
  app.kubernetes.io/managed-by=Helm

# 3. Deploy chart that defines extraConfigMaps.config
helm install adopt-demo charts/nginx-demo -n helm-internals \
  --set extraConfigMaps.config.status=managed-by-helm
```

Verify that `adopt-demo-config` was adopted and updated without errors:

```bash
kubectl get configmap adopt-demo-config -n helm-internals -o jsonpath='{.data.status}{"\n"}'
```

Output: `managed-by-helm`.

### Step 4: History retention and pruning (`--keep-history`)

By default, `helm uninstall` deletes all managed resources **and** purges all release Secrets from etcd.

If you need an audit trail or the ability to inspect an uninstalled release:

```bash
helm uninstall legacy-app -n helm-internals --keep-history
```

Check release history:

```bash
helm history legacy-app -n helm-internals
```

Output:

```text
REVISION    UPDATED                     STATUS         CHART               APP VERSION    DESCRIPTION
1           Tue Sep 22 17:51:45 2026    uninstalled    nginx-demo-0.6.0    1.30.4         Uninstallation complete
```

Notice the Secret still exists on the cluster:

```bash
kubectl get secret -n helm-internals -l name=legacy-app
```

To purge the retained release Secret permanently, run `helm uninstall` again without flags:

```bash
helm uninstall legacy-app -n helm-internals
```

Clean up the adopted release:

```bash
helm uninstall adopt-demo -n helm-internals
```

## Part D: Deprecated Kubernetes APIs and release migration (`mapkubeapis`)

When Kubernetes deprecates and removes an API (e.g. `policy/v1beta1` PodDisruptionBudget, `networking.k8s.io/v1beta1` Ingress), teams often update their chart templates to the new API version (`policy/v1`).

However, the subsequent `helm upgrade` frequently crashes with:

```text
UPGRADE FAILED: unable to build kubernetes objects from current release manifest: ... no matches for kind ... in version ...
```

### Why this happens

Helm reads the **current** release manifest from the release Secret to build the in-memory object tree for the three-way merge patch. If the old manifest contains an API version that the Kubernetes API server no longer recognizes, the API discovery client fails before Helm can even look at your new chart templates!

### Step 1: Install the `helm-mapkubeapis` plugin

Install the official Helm plugin for migrating release metadata:

```bash
helm plugin install https://github.com/helm/helm-mapkubeapis --version v0.6.1
```

Verify the plugin is installed:

```bash
helm plugin list
```

### Step 2: Deploy a release with PodDisruptionBudget

Install a release with `podDisruptionBudget.enabled=true`:

```bash
helm install pdb-demo charts/nginx-demo -n helm-internals --set podDisruptionBudget.enabled=true
```

### Step 3: Simulate a release stored with a removed API version

Modern Kubernetes clusters (v1.25+) removed `policy/v1beta1`. Let's simulate a release deployed on an older cluster by modifying `sh.helm.release.v1.pdb-demo.v1` to reference `policy/v1beta1`:

```bash
python3 -c '
import subprocess, base64, gzip, json

out = subprocess.check_output(["kubectl", "get", "secret", "sh.helm.release.v1.pdb-demo.v1", "-n", "helm-internals", "-o", "jsonpath={.data.release}"])
helm_b64 = base64.b64decode(out)
decompressed = gzip.decompress(base64.b64decode(helm_b64)).decode("utf-8")
obj = json.loads(decompressed)

assert "apiVersion: policy/v1\nkind: PodDisruptionBudget" in obj["manifest"]
obj["manifest"] = obj["manifest"].replace("apiVersion: policy/v1\nkind: PodDisruptionBudget", "apiVersion: policy/v1beta1\nkind: PodDisruptionBudget")

re_compressed = gzip.compress(json.dumps(obj).encode("utf-8"))
re_helm_b64 = base64.b64encode(re_compressed).decode("ascii")
re_k8s_b64 = base64.b64encode(re_helm_b64.encode("ascii")).decode("ascii")

patch = json.dumps({"data": {"release": re_k8s_b64}})
subprocess.check_call(["kubectl", "patch", "secret", "sh.helm.release.v1.pdb-demo.v1", "-n", "helm-internals", "-p", patch])
print("Secret patched with deprecated policy/v1beta1")
'
```

### Step 4: Trigger the failure

Attempt to upgrade `pdb-demo`:

```bash
helm upgrade pdb-demo charts/nginx-demo -n helm-internals --set podDisruptionBudget.enabled=true
```

Expected error:

```text
Error: UPGRADE FAILED: unable to build kubernetes objects from current release manifest: resource mapping not found for name: "pdb-demo-deployment" namespace: "" from "": no matches for kind "PodDisruptionBudget" in version "policy/v1beta1"
ensure CRDs are installed first
```

(Ignore the generic `ensure CRDs are installed first` hint: `PodDisruptionBudget` is a built-in kind; the real cause is the removed `policy/v1beta1` API.)

The release is stuck. You cannot upgrade it even though your chart has the modern `policy/v1` template!

### Step 5: Repair with `helm mapkubeapis`

Run `mapkubeapis` in dry-run mode:

```bash
helm mapkubeapis --dry-run pdb-demo --namespace helm-internals
```

Notice the output:

```text
Found 1 instances of deprecated or removed Kubernetes API:
"apiVersion: policy/v1beta1
kind: PodDisruptionBudget
"
Supported API equivalent:
"apiVersion: policy/v1
kind: PodDisruptionBudget
"
```

Now execute the in-place repair:

```bash
helm mapkubeapis pdb-demo --namespace helm-internals
```

Output:

```text
Set status of release version 'pdb-demo.v1' to 'superseded'.
Add release version 'pdb-demo.v2' with updated supported APIs.
Release 'pdb-demo' with deprecated or removed APIs updated successfully to new version.
```

`mapkubeapis` created revision 2 where the stored manifest uses `policy/v1`!

### Step 6: Re-run `helm upgrade`

Now re-run the upgrade command:

```bash
helm upgrade pdb-demo charts/nginx-demo -n helm-internals --set podDisruptionBudget.enabled=true
```

Expected output:

```text
Release "pdb-demo" has been upgraded. Happy Helming!
REVISION: 3
```

The upgrade succeeds cleanly!

## Part E: Helm 3 vs. Helm 4 Architecture & Evolution

| Architecture Feature | Helm 3 | Helm 4 |
| :--- | :--- | :--- |
| **Apply Engine** | Client-Side 3-Way Strategic Merge Patch | Kubernetes Server-Side Apply (SSA) |
| **Field Management** | Helm calculates client diff; Last-write-wins | `fieldManager=helm`; Conflicts detected via Kubernetes `managedFields` |
| **CRD Upgrades** | CRDs in `crds/` ignored on upgrade | Install-only by default; external CRD managers or dedicated charts recommended |
| **Failure Flags** | `--atomic` / `--cleanup-on-fail` | Streamlined flags (e.g. `--rollback-on-failure`) |
| **Force Flag** | `--force` | Replaced by `--force-replace` |
| **Post-rendering** | Executable binary only | Plugin-based post-renderers supported |
| **Chart Repositories** | HTTP Index (`index.yaml`) + OCI | First-class OCI registries + classic HTTP repositories |

### What Server-Side Apply (SSA) means for chart authors

In Helm 3, Helm merges the old Secret manifest, the live cluster state, and the new manifest locally on the developer machine or CI runner.

In Helm 4, Helm submits the rendered manifest using Kubernetes Server-Side Apply (`kubectl apply --server-side`). The Kubernetes API server itself tracks which manager owns which field (`managedFields`).

**Operational Takeaway:**
If your chart shares ownership of a field with an external operator or HPA (e.g., `spec.replicas`), Helm 4 with SSA will reject the change with a field conflict error unless ownership is transferred or explicitly ignored (`--force-conflicts`). Designing charts with clean field boundaries (such as omitting `replicas` when HPA is enabled) is essential for Helm 4 readiness.

## Break it and recover: Recovering a release stuck in `pending-upgrade`

### Introduce the failure

When a `helm upgrade` process is abruptly terminated (e.g., CI runner cancelled, network timeout, or SIGKILL), Helm leaves the release in the `pending-upgrade` state. While in this state, all future Helm commands are blocked:

```text
Error: UPGRADE FAILED: another operation (install/upgrade/rollback) is in progress
```

Let's simulate this failure on `internals-demo`:

```bash
# Find the latest release Secret
LATEST_REV=$(helm history internals-demo -n helm-internals | awk 'END{print $1}')
SECRET_NAME="sh.helm.release.v1.internals-demo.v${LATEST_REV}"

# Patch the release Secret payload to set status to pending-upgrade
python3 - "$SECRET_NAME" <<'EOF'
import subprocess, base64, gzip, json, sys
s = sys.argv[1]
raw = subprocess.check_output(["kubectl","get","secret",s,"-n","helm-internals","-o","jsonpath={.data.release}"])
obj = json.loads(gzip.decompress(base64.b64decode(base64.b64decode(raw))))
obj["info"]["status"] = "pending-upgrade"
enc = base64.b64encode(base64.b64encode(gzip.compress(json.dumps(obj).encode()))).decode()
subprocess.check_call(["kubectl","patch","secret",s,"-n","helm-internals","-p",
  json.dumps({"data":{"release":enc},"metadata":{"labels":{"status":"pending-upgrade"}}})])
EOF
```

Verify that Helm recognizes the release as stuck:

```bash
# Note: plain 'helm list' filters out pending releases; use --pending or -a:
helm list --pending -n helm-internals
```

Notice the status is `pending-upgrade`.

Now try to run an upgrade:

```bash
helm upgrade internals-demo charts/nginx-demo -n helm-internals
```

Observe the error:

```text
Error: UPGRADE FAILED: another operation (install/upgrade/rollback) is in progress
```

### Diagnose and recover

When a release is stuck in `pending-upgrade`, choose one of the following two alternative recovery strategies:

#### Option A: Roll back to the previous healthy revision (Standard Helm command)

When a previous stable revision exists in release history, use `helm rollback` to revert the stuck transaction:

```bash
helm rollback internals-demo -n helm-internals
```

Helm rolls back the release to the previous good revision and updates the pending revision's status. Verify recovery:

```bash
helm list -n helm-internals
```

#### Option B: Delete the pending Secret directly (Manual recovery)

If `helm rollback` is blocked or unavailable (for example, if the initial install failed into `pending-install`), delete the stuck transaction Secret directly from Kubernetes.

*(Note: If you already ran Option A above, re-run the python patch snippet to put the release back into `pending-upgrade` first before testing Option B).*

```bash
# Delete all pending-upgrade Secrets for the release (using label selector):
kubectl delete secret -n helm-internals -l owner=helm,name=internals-demo,status=pending-upgrade

# Verify the release can now be upgraded cleanly:
helm upgrade internals-demo charts/nginx-demo -n helm-internals --set replicaCount=1
```

*(Note: Deleting by label `status=pending-upgrade` ensures any older interrupted revisions left in `pending-upgrade` by Option A are cleared alongside the current one. In `helm history`, you may see non-consecutive revision numbers, which is normal).*

The release upgrades successfully!
